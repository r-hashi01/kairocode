# 0021 セッションの分岐: 過去のターンから、別のセッションとして続ける

- 状態: 承認（2026-10-21）
- 日付: 2026-10-21
- 関連: 要件 FR-4、FR-16・17（スナップショット、取り消し）、設計 2.1 節・7 節、不変条件 2・8、ADR 0007・0014（CLI のエンジン）

## 背景

要件 FR-4 は「セッションの過去の時点から、別の道を試せる（fork）」です。

KairoCode の会話は、ターンごとの履歴の頭（`TurnOutput.Head`、`kc_message` の鎖）で表せます。ターンの始まりと終わりの作業ファイルは、スナップショット（`Before`、`After`）として記録されています。

ただし、作業ディレクトリーは 1 つです。分岐したセッションと元のセッションが同じディレクトリーでファイルを書き換えると、互いに邪魔をします。

## 決定

1. **分岐は、新しいセッションを作ること。** 元のセッションは変えません。
   - `SessionInput` に `From`（元のセッションとターンの番号）と `History`（始めの履歴の頭）を足します（`omitempty`）。新しいセッションは、`History` から会話を始めます。
   - `History` は、分岐を作るときに、元のターンの記録された出力（`Head`）から取ります（記録された値。不変条件 2）。
   - セッションの ID は、ほかのセッションと同じく `s/<ID>` です（不変条件 8）。
   - 始めの履歴が空のセッションは、今と同じ呼び出しをするので、セッションの版は上げません。
2. **どこから:** `/fork [ターンの番号]`（既定は最後に終わったターン）と `kairocode fork <セッション> [ターン]`。
3. **作業ファイル:** 既定では触りません。会話だけを分けます。
   - `/fork <n> --files` で、新しいセッションの最初の出来事として、ターン n の終わりのスナップショットに作業ファイルを戻します（`restore`、冪等。`/undo` と同じ仕組み）。戻す前の状態もスナップショットに残るので、元のセッションの `/undo` と同じく取り戻せます。
   - 別の作業ディレクトリー（git の worktree）に分けることは、この ADR ではしません。
4. **CLI のエンジン:**
   - Claude Code: 最後のターンからの分岐は、Claude Code 自身の分岐（`--resume <id> --fork-session`）で、会話を引き継ぎます。それより前のターンからは分岐できないと伝えます（Claude Code の会話を、途中の時点に戻す手段がない）。
   - codex と copilot: 分岐の手段が確かめられていないので、分岐できないと伝えます。
5. **表示:** 新しいセッションの一覧と記録（ADR 0023）に、どこから分岐したか（`From`）を出します。

実装に現れるところ: `internal/workflows`（`SessionInput.From`、`History`）、`internal/runtime`（`Fork`）、`internal/server` と `internal/daemon`（API）、`internal/acp` と `internal/tui`（`/fork`）、`internal/cli`（`kairocode fork`）。

## 結果

- 過去のターンから、別の道を試せます。元のセッションは変わりません。
- 作業ファイルは既定で触らないので、分岐しただけで手元のファイルが変わることはありません。
- テスト（実装のとき足す）
  - ターン 1 から分岐したセッションの最初のモデルの入力が、元のターン 1 までの会話になる。元のセッションの記録は変わらない。
  - `--files` で、ターン n の終わりのファイルに戻る。戻した後に `/undo` で取り戻せる。
  - Claude Code の最後のターンからの分岐で、`--fork-session` で起動する（偽の claude）。それより前からは分岐できないと返る。

## 検討した代替案

- **元のセッションの中で巻き戻す（`/undo` の会話版）:** 元の道を失います。FR-4 の「別の道を試す」に合いません。
- **分岐ごとに git の worktree を作る:** 2 つの道を並べて動かせますが、ディレクトリーの作成と後片付け、ビルドの成果物の扱いが要ります。必要になったら別の ADR にします。

## 実装（2026-10-21）

- **セッション:** `SessionInput.From`（`ForkRef`）と `History` を足しました。セッションのワークフローは、`History` から会話を始めます。どちらも `omitempty` なので、前の記録の ID は変わりません。
- **`Runtime.Fork`:** 元のセッションの、終わった（`completed`）ターンの記録された出力（`Head`）と入力（エンジン、モデル、努力の度合い）から、新しいセッションを作ります。ターンを名指さなければ、最後に終わったターンからです。終わったターンがなければ `ErrNoForkPoint` です。
- **`--files`:** 新しいセッションに `EventForkFiles` を送り、そのターンの終わりのスナップショットに作業ファイルを戻すターンを動かします（`UndoInput.Fork`）。戻す前の状態（`Prior`）を、`/undo` の対象として記録するので、新しいセッションの `/undo` で取り戻せます。戻すのは、スナップショットにあるファイルだけです。その後にできたファイルは消しません。作業ディレクトリーは 1 つなので、元のセッションから見たファイルも変わります。
- **入り口:** サーバーの `POST /sessions/{id}/fork`、デーモンのクライアント、`kairocode fork [-files] <セッション> [ターン]`、ACP の `/fork [ターン] [--files]` です。ACP では、新しいセッションに進む手順（`kairocode chat -session <ID>`）を返事で伝えます。
- **決定から変えたこと（決定 4、CLI のエンジン）:** どのエンジンでも、どのターンからでも分岐できるようにしました。新しいセッションでは CLI のエンジンのセッションも新しく始まります。そのとき、エンジンを切り替えたとき（ADR 0014）と同じく、それまでの会話を最初の依頼に載せて渡します。
  - Claude Code の `--fork-session` は使っていません。最後のターンからしか分けられないためです。
  - 渡すのは会話の文面です（ツールの呼び出しは含まず、長さに上限がある）。CLI のエージェント自身の会話を引き継ぐ形よりは粗くなります。
  - Claude Code の最初の時期（`Epoch` 0）のターンは、これまで会話を渡していませんでした（進行中のターンの ID を保つため）。分岐したセッションのターンにだけ `TurnInput.Forked`（`omitempty`）を付け、会話を渡します。
- **テスト:** `TestForkFromATurn`（分岐した会話で続き、元は変わらない。最後のターンから。終わったターンがないとき）、`TestForkWithFiles`（ファイルが戻り、`/undo` で取り戻せる）、`TestForkOnClaudeCode`（Claude Code のセッションが新しく始まり、会話が渡る）。
- **durability-reviewer の指摘で直したこと**
  - ACP の `/fork` に読めない引数があるとき、セッションを作ってから「使い方」を返していました。いまは何も作りません（`TestACPFork`）。
  - 終わりのスナップショットを持たないターン（`/undo`、`/redo`、`/compact`）から `--files` で分岐すると、ファイルを戻さないまま「戻した」と答えていました。いまは、`/undo` と `/redo` のターンなら戻したスナップショットを、ファイルを変えないターンならその前の最も近いスナップショットを使います。どれもなければ `ErrNoSnapshot` を返します（`TestForkFilesFromAnUndo`）。
  - 元のセッションのターンが動いている間は、`--files` を断ります（`ErrForkWhileRunning`）。ターンのツールが使っているファイルを書き換えないためです。ほかのセッションが同じディレクトリーで動いている場合までは見ていません。
  - 元のターンがデーモンの既定のエンジンで動いていたとき、分岐はデーモンの既定のエンジンで始めます（前は、最後に選ばれたプロバイダーで始めていた）。
  - `POST /sessions` は、クライアントが送った `from` と `history` を捨てます。分岐を作れるのは `Fork` だけです。
- **残る弱さ:** 分岐はひとまとまりの操作ではありません。新しいセッションを作った後、ファイルを戻すターンを送る前にデーモンが落ちると、ファイルを戻さない分岐が残ります。そのときは、もう一度 `--files` で分岐してください。

## 追記（2026-10-28、承認（2026-10-28）: 失敗で止まったセッションを、最後のターンから続ける）

kairo-gap #16 の手当てです。ワークフローの中で `Child` や `Call` が保存先の一時的な誤り（SQLite の busy など）を返すと、セッションは会話の分岐を避けるために誤りで返り、kairo はセッション（根）を失敗として記録します。そのセッションには、もうメッセージを送れません。今は、送ると「session … ended before turn n」で止まり、利用者には何が起きたか、どう続ければよいかが分かりません。

決定（案）:

- **送る前に確かめる:** `Runtime.Send`（と画像つき、`/compact`、`/undo` などセッションへの出来事）は、セッションが失敗で終わっていたら、送らずに `ErrSessionFailed`（失敗の理由つき）を返します。閉じたセッション（`EventClose`）は、今までどおりです。
- **TUI:** `ErrSessionFailed` を受けたら、「このセッションは止まりました（理由）。最後に終わったターンから、新しいセッションで続けます」と書き、分岐（`Fork`、作業ファイルは今のまま: `files` なし）で新しいセッションを作り、同じメッセージをそこに送ります。画面のセッションは新しいものに切り替えます。元のセッションの記録は残り、`kairocode log` で見られます。
- **ACP と CLI:** ACP のセッションの ID はクライアントが持つので、切り替えません。`session/prompt` の誤りの文で「`kairocode fork <セッション>` か新しいセッションで続ける」と伝えます。`kairocode run -session` も同じ文を出します。
- **分岐の点:** 最後に `completed` で終わったターンです。失敗したターンの書きかけは、分岐した会話に入りません（そのターンの作業ファイルの変更は残っているので、「止まる前のターンが作業ファイルを変えたかもしれない」と新しいセッションの最初のメッセージに書き添えます。取り消しの書き添え（ADR 0011）と同じ形）。
- テスト（実装のとき）: 失敗で終わったセッションに送ると `ErrSessionFailed` が返り、何も送られない。TUI では新しいセッションに切り替わって、同じメッセージが送られ、書き添えが入る。ACP では誤りの文に続け方が出る。
- 検討した代替案:
  - **セッションの失敗を記録しないで、後でやり直す（kairo の側で直す）:** 本来の直し方です。kairo の ADR の案として出します（#16）。それまでの間、行き止まりにしないための手当てがこの追記です。
  - **ACP でも黙って分岐して、内部のセッションを差し替える:** クライアントの ID と内部の ID がずれ、`session/load` と記録の閲覧が分かりにくくなります。
- **実装（2026-10-28）:**
  - 失敗の見分け方: kairo は、コードで書くワークフローの失敗を「`completed` で、`done` が `ok: false`」として記録します（`Status` は `failed` にならない）。そのため、終わったセッションに `kairo.Await` を呼び、`WorkflowError` が返るかで見分けます（`Runtime.failed`）。セッションへの出来事（`Send`、画像つき、`/compact`、`/undo`・`/redo`）はすべて `signal` を通るので、そこで確かめます。
  - デーモンの API は 410 を返し、クライアントは `runtime.ErrSessionFailed` に戻します。ACP は誤りの符号 `-32010`（`CodeSessionFailed`）で返し、ACP のクライアントも `ErrSessionFailed` に戻します。続けるための拡張のメソッド `_kairocode/go_on`（分岐し、新しいセッションを ACP のエージェントに覚えさせる）を足しました。TUI はこれを呼んで、新しいセッションに切り替え、書き添え（`runtime.FailedNote`）を付けて同じメッセージを送ります。
  - CLI: `kairocode run` はいつも新しいセッションを作るので、失敗したセッションに送ることはありません（`-session` は無かった）。
  - テスト: `TestSendToAFailedSession`（失敗で終わる試しのワークフローで、送れずに理由が返る）、`TestPromptToAFailedSession`（ACP）、`TestGoOnFromAFailedSession`（TUI）。本物の保存先の誤りで失敗したセッションからの分岐は、テストでは作れていません（分岐そのものは ADR 0021 のテストで確かめている）。
